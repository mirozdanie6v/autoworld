# AWG — резервное копирование Яндекс YDB в Cloudflare D1

Дата: 15.10.2026. Контур: **Автомир Грузия**, `mirozdanie6v/autoworld`.

## Область покрытия

Источник: YDB Serverless `etn00ojk5iv1u7dgpdar`, production `awgcars.ru`. Перенос на Timeweb отменён; исходный production **остаётся на Яндекс Cloud**.

Бэкап состоит из согласованного `snapshotReadOnly` в YDB:
- бизнес-таблицы `auto_sale_leads`, `auto_sale_quotes`, `auto_sale_orders`, `auto_sale_payments`, `auto_sale_notes`, `auto_sale_team`, `auto_sale_catalog`, `auto_sale_telegram_bindings`;
- `auto_sale_state_meta` (ревизия и версия схемы);
- привязки и доступы `auto_sale_admin_access`;
- `auto_sale_notification_outbox` (очередь и история доставки сообщений).

Экспорт использует имеющиеся `createRecoveryBackup` и `validateRecoveryBackup`. Проверяются версии строк, уникальность ключей, контрольные суммы и наличие доменных таблиц. **Не охватывает** остальные независимые Яндекс-базы других проектов, Yandex Object Storage (изображения), журнал Yandex Cloud или PostgreSQL; для них потребуются отдельные источники и место хранения. Ранее существующая legacy `auto_sale_state` не включена в формат `awg-recovery-v1`: бэкап ориентирован на текущую авторитетную нормализованную модель.

## Целевая система

Cloudflare account: `f4935962036fd500d34335e0b174b227`.

D1 database: **`awg-ydb-backup-archive`**. Она не связана с продакшеном и не заменяет YDB. База создаётся только при **явном ручном запуске с флагом `create_database=true`**.

В D1:
- `awg_backup_manifest` — ID, время, ID исходной БД, ревизия, версия схемы, размеры, SHA-256 архива, checksum восстановимого содержимого, статус `writing/verified`;
- `awg_backup_chunks` — последовательные фрагменты **только зашифрованного** сжатого архива (до 28 000 символов на строку).

Перед отправкой: gzip + AES-256-GCM с уникальным случайным 96-битным nonce, дополнительными аутентифицируемыми данными, отдельным 256-битным ключом. Обработка несжатых персональных данных происходит только в оперативной памяти GitHub runner; код не выводит содержимое или ключи в журналы. SHA-256 всех фрагментов и расшифровка после обратного чтения защищают от испорченных или незавершённых загрузок. Непроверенные копии остаются со статусом `writing` и не будут приняты для восстановления.

### Расписание и контроль

GitHub Actions: [AWG encrypted YDB backups to Cloudflare D1](../.github/workflows/backup-awg-ydb-cloudflare-d1.yml).

План — **каждые 6 часов (UTC 00:17, 06:17, 12:17, 18:17)**; GitHub Actions может отложить запуск. Каждый запуск создаёт новую версию; прекращение записи в Яндекс Cloud не требуется. Входящий Telegram webhook, VK ID, API Gateway и контейнер приложения не меняются.

Расписание намеренно **неактивно**, пока GitHub Actions Variable `AWG_CF_D1_BACKUP_ENABLED` не имеет значения `true`. Если запись невозможна, workflow завершается с ошибкой; архив со статусом `verified` при этом не создаётся. Следите за ошибками в GitHub Actions. Удаление старых копий **по умолчанию отключено**: прежде чем включать ротацию, нужно согласовать срок хранения и проверить квоту/стоимость D1. Для больших архивов (лимит 24 MiB в D1) механизм остановится с ошибкой и потребует адаптации под Cloudflare R2.

## Обязательная настройка (без передачи секретов в чат)

Проверка 15.10.2026: старый `CLOUDFLARE_API_TOKEN` дал HTTP **401** на D1 API, а секрет `AWG_BACKUP_ENCRYPTION_KEY` отсутствовал. Пока эти проблемы не исправлены, **действующих облачных бэкапов нет**.

1. В Cloudflare Dashboard → My Profile → API Tokens создайте отдельный токен с разрешением **Account → D1 → Edit** для указанного Cloudflare-аккаунта. Не расширяйте права Telegram relay токена.
2. В GitHub репозитории → Settings → Secrets and variables → Actions → Secrets создайте:
   - `AWG_CF_D1_BACKUP_TOKEN` — новый отдельный токен Cloudflare D1.
   - `AWG_BACKUP_ENCRYPTION_KEY` — `base64` случайного ключа 32 байт (команда локально: `openssl rand -base64 32`). Сохраните **вторую копию ключа отдельно от GitHub**, в защищённом хранилище: без него восстановление зашифрованных данных будет невозможно. После создания и проверки бэкапов не меняйте ключ без процедуры ротации.
3. В GitHub Actions откройте workflow `AWG encrypted YDB backups to Cloudflare D1` → **Run workflow**, `operation=backup`, `create_database=true`. Эта первая операция создаст только базу `awg-ydb-backup-archive`, таблицы архива и **первый реальный зашифрованный снимок**, затем скачает его обратно для проверки.
4. Проверьте появление `AWG_YDB_CLOUDFLARE_BACKUP_SUCCESS` и статус `verified=true` в журнале.
5. Запустите `operation=verify-latest` без создания БД. Должна появиться строка `AWG_CLOUDFLARE_D1_RESTORE_DRILL` с `ok=true` и `restoredToProduction=false`.
6. В GitHub → Settings → Secrets and variables → Actions → Variables создайте `AWG_CF_D1_BACKUP_ENABLED=true`. После этого задания пойдут автоматически по расписанию.
7. Для аварийного скачивания без обращения к Яндексу вручную запустите `operation=download-latest` (без `create_database`). В артефактах GitHub Actions появится `awg-cloudflare-encrypted-recovery`, срок хранения **7 дней**. Внутри файл `.enc`, совместимый с форматом `awg-encrypted-recovery-v1`. Он остаётся зашифрованным; сохранить его и исходный ключ отдельно. Получение артефакта само по себе ничего не восстанавливает.

## Безопасность и восстановление

Никогда не используйте D1 как вторую рабочую CRM-базу и не сохраняйте туда PII в открытом виде. Ссылка, ID записи или SHA **не являются ключом дешифрования**.

`verify-latest` выполняет репетицию чтения зашифрованных фрагментов из Cloudflare, расшифровки в памяти и восстановления логической модели по нормализованным строкам. Она ничего не пишет в Yandex YDB. Для настоящего восстановления после аварии потребуется отдельный согласованный процесс: создать **новую изолированную YDB**, снять дополнительную копию исходного состояния (если возможно), проверить доступы, выполнить перенос с предварительным dry-run, сверить числа сущностей, версии, статус сообщения и только затем менять маршруты. **Автоматического восстановления поверх production нет.**

### Ограничения

- Невозможно обещать нулевую потерю данных: максимально ожидаемое окно — около 6 часов плюс возможное опоздание GitHub Actions или ошибка экспорта.
- Если Yandex недоступен в момент запуска, новые копии не создаются; ранее проверенные D1-копии сохраняются.
- После включения регулярно контролируйте квоту Cloudflare D1, историю успешных запусков и ключ шифрования.
- Этот workflow не создаёт резервную копию **самого Cloudflare D1**; для долговременной защиты стоит добавить независимую периодическую копию в R2 или другой регион после проверки расходов.

Проверка и скачивание уже существующей D1-копии **не используют Yandex IAM или YDB**: даже при полном отказе Яндекса можно получить и проверить последний успешно зашифрованный архив из Cloudflare. Операции записи в Cloudflare и скачивания нельзя выполнять без отдельного токена `AWG_CF_D1_BACKUP_TOKEN`. Срок GitHub-артефакта не заменяет срок хранения D1-версий.
